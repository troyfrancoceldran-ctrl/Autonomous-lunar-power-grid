The headline finding

The simulation modelled the lunar night as 336 hours — the familiar “14 Earth days” shorthand. That figure is the Moon’s rotation period halved. A power system does not care about rotation; it cares when the Sun comes back, which is the synodic period of 29.53 days, or 708.7 hours.

“…capability for at least 354 hr of nighttime energy storage.”
NASA Fission Surface Power — extended surface mission requirement
As modelled
336.00 h
Synodic actual
354.35 h

18.35 h of every night went unmodelled — 5.1 % of the design case. Night energy demand rises from 1 737 kWh to 1 832 kWh, taking the nominal night from 77 % to 81 % of total stored reserve.

Nothing outside config.py required editing. Every module derives its timing from those constants, so the corrected period propagated through the environment model, both generation assets, both storage devices and all four loads without a line changing. That was the point of the constraint.

Findings register

F-01

Lunar night understated by 5.1 %

High Closed NASA FSP

Day and night were set to 14 × 24 = 336 h, conflating the tidally-locked rotation period with the synodic day. Corrected to 708.7 / 2 = 354.35 h each. SIM_DURATION_DAYS raised 56 → 60, because at the true cycle length 56 days covered only 1.90 synodic cycles against a stated requirement of at least two.

F-02

PV square wave silently assumes a sun-tracking array

High Closed — W01 Solar geometry · NASA VSAT

Irradiance returns a flat 1.0 for the whole lunar day. That is only true for a two-axis tracker or a NASA-style Vertical Solar Array. A fixed horizontal array at an equatorial site sees output vary as the sine of solar elevation, averaging 2/π = 0.637 of peak — so the model overstated daily energy by 36 % unless tracking is declared.

Resolved in caf29c9. solar_elevation_fraction() returns sin(π · phase / LUNAR_DAY_HOURS) during the day and 0.0 at night, with the phase modulo factored into a shared _phase_hours() helper so the terminator is defined in exactly one place. solar_irradiance_fraction() deliberately stays a square wave: it answers is there sun, the new method answers how much, and PVArray selects between them. Verified against nine reference values; measured mean elevation over daylight 0.619.

Method note. The first two implementations passed all nine spec values while is_daylight() was returning True at midnight — the defensive max(0.0, …) clamp was absorbing a raw sine of −0.96 at deep night and reporting a plausible 0.0. The verification table alone could not see it; an invariant sweep asserting that is_daylight varies with t caught it immediately. A guard that silently corrects a fault also hides it, and tests must assert on the gate, not only downstream of it.

F-03

The reactor never fails

High Closed — W03 NASA FSP autonomy

FSP_AVAILABILITY = 1.0 models a reactor that is online every hour of a ten-year life. NASA’s requirement set assumes autonomous start and stop precisely because outages happen. Worse, the contingency was survivable-by-luck rather than by design: with the battery flat and the tanks at 95 %, an aggregate state-of-charge signal reads 0.872 while a reactor outage leaves 7.5 kW of load unserved — including part of life support.

Resolved in 139da44 and e16d036. FissionSurfacePower takes a scripted outage window, half-open (start ≤ t < start + duration) and firing once rather than per cycle, so contingency behaviour is reproducible instead of stochastic. Default config leaves FSP_OUTAGE_START_HOURS = None; the scenario switches it on. The second half of this finding — the outpost having no way to notice the 7.5 kW deficit — is closed by W04's shortfall_w signal.

Guard note. The window test is is not None, never truthiness. An outage beginning at t = 0.0 — cold start with the reactor still offline — is a legitimate scenario, and if self.outage_start_hours: would silently read it as disabled. Legal Python, wrong answer, no error. Verified explicitly.

F-04

No lunar dust derate on the array

Medium Closed — W02 NTRS 19910020924

NASA measurements show cell short-circuit current falling exponentially with deposited dust mass, and every nearby landing adds more — roughly 0.28 mg/cm² at 2 km after ten missions. Regolith is also an insulator, so it degrades radiator performance at the same time. PV_DUST_DERATE is a fixed stand-in for a mechanism that genuinely worsens across mission life.

Resolved in 139da44. PVArray now takes dust_derate and sun_tracking. The derate is kept separate from packing_factor although both are dimensionless multipliers near 1: packing factor is array geometry and wiring, dust is a surface condition, and only one of them becomes a function of mission elapsed time in a later revision. Collapsing them would destroy that seam. Dusted peak 34 909.65 W, down from 36 747 W.

Design note. sun_tracking selects the daily profile through an if/else; it does not scale the output. A first implementation multiplied by the boolean instead, and since PV_SUN_TRACKING is False, the array produced 0 W at every hour of the run — including local noon. A bool used as a factor can only annihilate or do nothing; used as a branch it states which site is being modelled. The peak-output-over-a-cycle assertion that caught this belongs in the test suite for every source: a generator that never generates is a test failure, not a quiet result.

F-05

Run duration below the two-cycle requirement

Medium Closed Project requirement

Consequential to F-01: the 56-day run was written against the 672 h cycle. At 708.7 h it captured 1.90 cycles, so the second charge/discharge round trip never completed and any cumulative drift in stored hydrogen would have gone unobserved. Now 60 days — 2.03 cycles.

F-06

95 % battery depth of discharge left unjustified

Low — defensible Closed LEO practice · lunar rover

LEO spacecraft hold depth of discharge below 30 %, and a lunar rover battery is capped at 38 %. A BATTERY_SOC_MIN of 0.05 looked reckless beside those figures. It is not — but only because of cycle count: a surface system sees one cycle per synodic period, about 124 across a ten-year life, against roughly 50 000 in LEO. The justification is now recorded in config.py, with a note that it must be revisited if the mission profile changes.

What already complies

Six design decisions made earlier in the build turn out to match established practice. Worth recording, because they were reasoned from first principles rather than copied.

One caveat carried from that last row: the same literature warns that battery-priority dispatch is “feasible and economical for short-term operation” but “does not account for seasonal variations… which will result in a lack of pre-stored hydrogen and load losses in long-term operations.” The 60-day run is the test — if the fuel cell finishes each cycle lower than it started, the architecture does not close.

Declared simplifications

Not findings. These are boundaries of the model, and the difference between an engineering simulation and an ideal machine is whether they are stated or discovered.

SimplificationWhat reality adds
RFC is an energy model, not a mass model No tankage, stack or radiator mass; no thermal parasitics; no pressure dependence — NASA reports ~4 points of round-trip efficiency between 27.6 and 10.3 MPa. The 33 333 Wh/kg here is hydrogen’s heating value; NASA’s system-level target is 110 → 550 Wh/kg.
No degradation over mission life Array output and battery capacity both fade. Currently only dust is represented, and only as a constant.
No survival or dormant mode NASA separates nominal operations from survival, where thermal control plus essential life support falls to 1–3 kW. The CRITICAL tier here is a flat 6.5 kW with no lower gear.
No IEEE 2030.7 transition function Genuinely not applicable — a lunar grid is permanently islanded and never reconnects to a utility.

Solar elevation profile

environment.py · closes F-02

The Sun’s intensity doesn’t change across the lunar day — there is no atmosphere to attenuate it. What changes is the geometry between the Sun and a fixed array. So this belongs in the environment as a second, separate question, leaving solar_irradiance_fraction exactly as it is:

solar_elevation_fraction(t_hours) -> float
    phase = (t_hours + start_phase_hours) % LUNAR_CYCLE_HOURS
    if phase >= LUNAR_DAY_HOURS:   return 0.0
    return sin(pi * phase / LUNAR_DAY_HOURS)
  • 0.0 at sunrise, 1.0 at local noon, 0.0 at sunset; mean 0.637.
  • Needs import math, and a shared _phase_hours() helper so this and is_daylight cannot disagree about where the terminator falls.
  • Whether the array uses this is a property of the array, not of the Moon — which is why the flag lives on PVArray, not here.

Array derating and tracking

assets/generation.py · closes F-04, consumes W01

PVArray.__init__ gains dust_derate=PV_DUST_DERATE and sun_tracking=PV_SUN_TRACKING. The power chain then becomes:

geometry = (environment.solar_irradiance_fraction(t_hours)
            if self.sun_tracking
            else environment.solar_elevation_fraction(t_hours))

return (SOLAR_CONSTANT_W_PER_M2 * self.area_m2 * self.efficiency
        * self.packing_factor * self.dust_derate * geometry)
  • Both branches already return 0.0 at night, so no extra guard is needed.
  • Expect peak to fall 36 747 → 34 910 W from dust alone, and daily energy to fall a further 36 % once tracking is off.
  • That is a large reduction. Re-check the night energy balance afterwards — PV_AREA_M2 may need to grow, which is itself a realistic finding.

Outcome — the array was not resized. Peak fell as predicted to 34 909.65 W and daylight energy to 62 % of the square-wave figure, but the 60-day balance still closes with 0 kWh unserved. Generation is 134 % of demand (PV 15 826 kWh + FSP 14 400 kWh against 22 572 kWh drawn); the RFC reserve floor merely narrows from 0.241 to 0.174. Daylight surplus of 11 749 kWh far exceeds the 4 720 kWh needed to refill the tanks, so surplus was never the binding constraint — and extra area buys almost nothing, 200 m² lifting the floor only to 0.203. PV_AREA_M2 stays at 100 and the narrower margin is recorded as the honest cost of removing two flattering assumptions.

Reactor outage window

assets/generation.py · closes F-03

FissionSurfacePower gains outage_start_hours and outage_duration_hours from config:

if (self.outage_start_hours is not None
        and self.outage_start_hours <= t_hours
        < self.outage_start_hours + self.outage_duration_hours):
    return 0.0
return self.rated_power_w * self.availability
  • Scripted rather than stochastic, so a contingency run is reproducible and a reviewer can see exactly what was tested.
  • Note what this does to the docstring: t_hours has been “deliberately unused” since Step 3. It is now load-bearing. The uniform signature that looked like ceremony turns out to have been foresight.

Dual-signal control interface

base_asset.py · controller.py · power_bus.py

The Step 8 design decision, resolved in favour of defence in depth. An energy-limited failure and a power-limited failure are different events; one detector cannot see both. PowerStorage gains three read-only properties:

deliverable_energy_wh        # what I could still put on the bus, after losses
deliverable_capacity_wh      # what I could put on the bus when full
available_discharge_power_w  # what I could deliver right now, this instant
  • Fractions cannot be summed across devices of different sizes — the battery holds 7.9 % of the reserve but would carry 50 % of the vote in a naive average. Energy-weighted aggregation is what the equivalent-state-of-charge literature specifies, and each device must therefore report watt-hours, not a percentage.
  • ControlStrategy.update() gains a shortfall_w argument: max(0, demand − generation − available storage power). Positive means this hour browns out unless load is shed now.
  • Every term is measurable at the start of the tick, so this is a real-time calculation and not a forecast — which keeps it inside IEEE 2030.7’s core-function rule.
  • The controller acts before dispatch, on state carried from the previous tick. Sample, decide, actuate, let the hour play out — the same loop the microcontroller will run.

Outcome — two properties, not three. available_discharge_power_w(dt) turned out to be min(rating, deliverable_energy_wh / dt), both operands already interface members, so the expression is identical for every storage device that will ever exist. It was made concrete on PowerStorage rather than abstract — the same reasoning Load.effective_demand() already applies. It also takes dt_hours: 100 Wh is 100 W over an hour and 1000 W over six minutes, and a ceiling ignoring the step would report full nameplate power for a device with minutes left.

Measured, both devices at nameplate: battery 180 500 Wh deliverable and 50 kW; RFC 2 090 000 Wh and 12 kW; fleet 2 270 500 Wh and 62 kW. The battery is 7.95 % of fleet reserve — the figure that rules out a mean-of-SoCs aggregate. In the motivating case (battery at floor, tanks 0.95) the fleet reports aggregate_soc 0.872 alongside a 12 kW ceiling and 7.5 kW unserved against a 19.5 kW night load. Both numbers correct; neither sufficient alone.

Control note. The controller runs three branches — power emergency, energy low, recovery — and the emergency branch bypasses the dwell timer, the only place in the file that does. Dwell prevents chatter around a threshold; an unserved-power event is not chatter but a live failure, and an uncontrolled brownout drops loads in whatever order physics chooses. Recovery is gated on both signals: without that, the controller sheds on power and restores on energy every tick, because reserves read healthy precisely because the shed loads are not drawing from them. CRITICAL is excluded from both shed branches — ECLSS survives eight consecutive emergency ticks at aggregate_soc 0.05.

What the remediation taught

Three of the four work orders failed their first implementation, and every failure shared a shape worth recording: a value used in the wrong grammatical role, producing a plausible number rather than an error.

  • is_daylight returned start_phase_hours < LUNAR_DAY_HOURS — constant, so the lunar night ceased to exist. All nine reference values still passed, because the clamp absorbed the negative sine at midnight.
  • PVArray multiplied by the sun_tracking boolean instead of branching on it. False == 0, so the array produced 0 W at every hour of the run.
  • The RFC's two new members were written without @property, so they returned bound methods. The abstract declaration did not catch it — Python checks only that the name exists — and the failure surfaced two files away, in the base class's division and in the fleet sum.

None of these raised an exception at the point of the mistake. The tests that caught them were not value comparisons but invariants: does is_daylight vary with time; does the array ever generate; is this member actually a property. Step 11's suite should assert those directly.

On the verification itself. Three of the checking harnesses written during this remediation contained errors of their own — an expected value computed at the wrong hour, a device chosen in the rating-limited regime for a test of energy-limited scaling, and load names retyped as string literals rather than read from the classes. A test that fails for its own reasons is cheap; a test that passes for its own reasons is what let the first two W01 implementations through. The asymmetry is worth remembering.
